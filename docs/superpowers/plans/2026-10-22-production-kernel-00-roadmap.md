## 3. 全局约束（每个计划都必须遵守）

1. 只在功能分支 `refactor/production-kernel` 上工作。开始前先用 `git branch --show-current` 确认分支；工作区有不属于本计划的未提交改动时，先停下报告，不得暂存、丢弃或一并提交。不得切换到其他分支提交，也不得创建新的 worktree。
2. 遵守 `AGENTS.md`：数据保护、AI-First、质量门不阻塞、运行记录只读、UI 文案、文件长度与目录规则、Prompt Governance。
3. **V1 冻结**：`services/novel/director/`、V1 工作流，以及旧生产代码（`services/novel/runtime`、`production`、`state`、`fact`、`dynamics`、`quality`、`chapterEditor`）**不得修改行为**。唯一例外是计划 08，它只允许删除 V2 分支。
4. 内核代码放在 `server/src/modules/production/`。领域层不得有 IO、时钟、随机数，只能导入本目录与 `modules/production/common/`。
5. 内核不得导入 `modules/director`、`services/novel/director`、`modules/novel/director-routing`、`services/novel/workflow`、`modules/novel/short-story`。短篇只能从 `modules/production/common/index.ts` 导入，不得导入内核的其他部分。
6. 不得连接或迁移开发数据库。需要数据库的测试一律使用临时 SQLite，并加入 `server/scripts/run-tests.cjs` 的 `integrationTests`。快速测试不得访问数据库。
7. 新增 Prompt 必须是注册在 Registry 里的 PromptAsset。
8. 提交规则：
   - **本地例外：北京时间 18:00 之前，默认不单独提交。** Task 完成后先保持改动未提交，并确保工作区只包含本计划的改动，供验收检查。18:00 之后，或用户明确要求时，再按阶段提交。这条本地规则优先于"每个阶段完成后提交"的通用要求。
   - 提交标题以 `优化：`、`新增：` 或 `修复：` 开头。
   - 纯内部改动不更新发布说明，并在提交说明里写明这一点。
   - 计划中出现的提交命令，都只在上述条件满足时才执行。
9. 不新增第三方依赖。
10. 只用 `git add <具体文件>`，禁止 `git add -A` 和 `git add .`。

报告格式：`docs/superpowers/reports/production-kernel/<计划编号>-<日期>.md`，内容包括已完成的 Task、未完成的 Task、遇到的停止条件、相关命令输出、涉及文件。

## 5. 执行协议

1. 先读本文件、设计文档和对应计划。
2. 按 Task 顺序执行。每个 Task 先写测试并看到它失败，再写实现，再看到测试通过。
3. 不得跳过、合并或改写计划里的验收命令。
4. 完成或停止时写报告。

## 6. 验收流程（由我执行）

1. 检查提交范围：`git diff --stat <基线>..HEAD`，确认没有超出计划。
2. 冻结检查：确认第 3 节第 3 条列出的目录没有差异（计划 08 除外）。
3. 运行计划中的验收命令，以及 `pnpm --filter @ai-novel/server build`。
4. 变异检查：对关键规则做最小破坏，测试必须失败。
5. 边界检查：用 `rg` 检查导入方向、领域层是否有 IO、文件长度。
6. 写验收结论：通过，或列出需要返工的项目，再交回执行者。
