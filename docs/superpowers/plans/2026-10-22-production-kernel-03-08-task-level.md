## 计划 03：应用层与适配器

**目标：** 让内核能真正跑完一章。具体包括：执行器循环调用 `decideNext`，执行对应阶段，再写回进度；定义端口；用适配器把现有的底层服务接到端口上；新增单元进度表。

**新增内容：**

| 路径 | 职责 |
| --- | --- |
| `modules/production/application/ports.ts` | 定义端口：`StagePort`（每个阶段一个）、`StoryStatePort`、`UnitProgressStore`、`BudgetPort`、`Fence` |
| `modules/production/application/unitExecutor.ts` | `runUnit(request): Promise<UnitOutcome>`，只包含"决策 → 执行 → 写回"这一个循环 |
| `modules/production/infrastructure/stages/*.ts` | 每个阶段一个适配器，调用现有服务 |
| `modules/production/infrastructure/storyState/*.ts` | 故事状态端口的适配器，按计划 01 Task 5 的结论实现 |
| `modules/production/infrastructure/progressStore.ts` | 单元进度表的仓储 |
| `modules/production/profiles/longChapter.ts` | 长篇默认配置，另附快速和严格两个变体，参数来自计划 01 |
| Prisma：`ProductionUnitRun` | 按调用方 ownerKey + chapterId 唯一区分每次作业的章节进度，记录所选稿件、内容哈希和版本号。两套 schema 与两个迁移目录同步修改；每个迁移只建一张表。新增表提案已获用户批准 |

**关键规则：**

- 适配器调用旧服务时显式传参，不进入旧 V2 生产调度。用户已批准 `03-reconcile-boundary.md`：抽取与回填编排移入新内核，允许复用已盘点为保留的共享持久写入保护；旧目录不修改。
- 适配器不得修改旧服务。旧服务不满足需要时，按停止条件 G1 停下，由我决定是否把实现复制进内核。
- `commit` 阶段经由生命周期入口写入；原服务不支持事务版本检查，用户已批准 `03-lifecycle-exception.md` 的最小隔离方案，由新内核的 `ProductionChapterLifecycleService` 在同一事务保存正文与回执，旧服务保持冻结。
- 凡是调用模型的阶段，执行前先查同一内容哈希下是否已有结果，有就复用，不再调用模型。
- 新表需要用户批准；只生成迁移文件并在临时库上验证，不对开发库执行迁移。

**验收要点：**

- 临时库集成测试：一章从无正文走到完成。
- 分别在 `draft` 之后、`repair` 之后、`commit` 之后模拟崩溃，重跑后结果相同，并且不重复调用模型。
- 用户在运行中修改正文时，旧结果不落库。
- 冻结目录的差异为空。

## 计划 04：共用约定与小工具

**目标：** 建立 `server/src/modules/production/common/`。长篇内核和短篇都从这里获取约定与小工具，不再各自实现。

**内容（以计划 01 Task 4 第 3 节中归属为 `common` 的项为准）：**

| 类别 | 内容 |
| --- | --- |
| 约定 | 质量债结构；问题策略语义；停止判定（什么情况才能停止整条生产）；编辑保护规则 |
| 小工具 | 补丁应用（先统一定位，再校验唯一且互不重叠，最后从后往前应用；任何一步失败都返回完整原文）；带版本围栏的保存；用量与预算记账；上下文预算校验（估算输入 token 数并与有效预算比较） |

**关键规则：**

- `common/` 不依赖内核的 `domain`、`application`、`infrastructure`，也不依赖短篇模块。
- `common/` 必须有自己的 `index.ts`；外部只能从这个入口导入。
- 只新增，不替换。旧代码和短篇改为使用 `common/`，分别在计划 05、06 中进行；本计划不修改任何调用方。
- 补丁应用必须覆盖 `docs/wiki/debugging/recurring-failure-modes.md` 中"补丁重叠"一节描述的失败情形。
- 上下文预算校验属于输入安全校验，只做数字比较，不做任何语义判断。

**验收要点：**

- 纯函数测试覆盖补丁应用的以下情形：成功、不唯一、缺失、重叠、无变化、删除。
- 质量债结构能无损表达长篇和短篇两边现有的质量债字段（对照计划 01 Task 4 第 3 节）。

## 计划 05：V2 长篇正文切换到内核（验收者执行）

**目标：** `modules/director/steps/production/chapterBatch.ts` 不再启动并等待旧的流水线作业，改为在授权范围内逐章调用内核。

**关键规则：**

- V2 内核（`modules/director`）仍不导入 `modules/production`，由 `app/director` 的生产组装负责注入。
- 运行记录的所有权围栏、预算和问题策略快照，都从运行契约注入内核。
- 单元结果映射为 V2 的产物、质量债和停止信号。映射写成纯函数，并配测试。
- 已经在旧流水线上运行中的批次，继续由旧流水线完成；新批次才走内核。进行中的作业不迁移。
- 增加开关 `PRODUCTION_KERNEL_V2_CHAPTERS`，默认关闭。

**切换前必须完成：** 决策差异清单。用同一组夹具对比内核与旧流水线的阶段决策，列出全部差异，并经用户确认。

**验收要点：**

- V2 全部测试通过。
- 回放夹具全部通过。
- 临时库演练覆盖"一个批次 3 章，第 2 章需要修复，第 3 章在运行中被用户编辑"。

## 计划 06：短篇挂到 V2 运行记录

**前置：**

- 计划 04 已验收；
- 进行中的短篇开发（`codex/short-story-revision-recovery`，包括其中尚未提交的改动）已经提交并合入 `main`；
- 已按合入后的代码重做计划 01 Task 4；
- 用户已确认短篇在导演台和运行记录中的呈现方式与文案。

**目标：**

1. 在 V2 中注册一份短篇计划：短篇计划 → 逐段写作 → 全篇审校 → 单次修复。可以在短篇计划之后设一个确认门，用于半自动。每一步由一个步骤适配器调用 `modules/novel/short-story/` 的生产逻辑。
2. 短篇不再依赖 V1 工作流任务（以计划 01 Task 4 第 2 节的清单为准）。
3. 补齐修后核对：修复之后再做一次全篇审校，未通过时保留修复前的正文并记录质量债。
4. 全篇审校前做上下文预算校验；超出预算时暂停，并给出"更换上下文更大的模型"的指引，不硬审。
5. 短篇的质量债、编辑保护和补丁应用改为使用 `modules/production/common/`。

**关键规则：**

- 短篇的生产逻辑留在短篇模块，不进入内核。
- 短篇只依赖 V2 的稳定内核（运行记录、控制状态、产物台账、守卫、命令），不复用任何长篇步骤。
- V2 内核不得出现"如果是短篇"的分支。遇到必须这样写的情况时，按停止条件 G6 停下，由我判断如何补成通用能力。
- 面向用户的文案用"创作进度"一类说法，不出现"导演"；遵守 `AGENTS.md` 的 UI 文案规则。
- 历史短篇任务只读保留，不做转换；新开的短篇才走 V2。
- 继续满足短篇 README 中的运行时不变量：连续正文投影、人工编辑过的片段不被覆盖、`expectedVersion` 校验、自动修复最多一次、质量债不阻塞。
- 增加开关 `SHORT_STORY_ON_V2`，默认关闭；关闭时短篇的行为与改动前完全一致。

**验收要点：**

- 开关关闭时，短篇现有测试全部通过。
- 开关打开时，临时库测试覆盖以下情形：生成；中途崩溃后恢复；人工编辑后重新生成；全篇审校后单次修复并完成修后核对；上下文预算超出时暂停。
- 用 `rg` 确认 V2 内核中没有短篇专属分支。
