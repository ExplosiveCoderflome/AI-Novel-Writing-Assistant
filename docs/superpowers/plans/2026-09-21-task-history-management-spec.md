# 运行记录与导演跟进软删除清理规格

## 背景

“运行记录”和“导演跟进”积累了大量早期失败、取消和完成记录。很多错误在后续操作后已经没有参考价值，但仍持续占据列表与异常视线。当前后端已有 `TaskCenterArchive` 归档标记，实质上已经具备软删除基础，只是没有批量入口、归档列表和恢复能力。

本阶段只解决“历史记录很碍眼，用户需要快速清掉”的问题，不把任务生命周期重构、自动判断错误是否已经解决或历史保留策略作为前置条件。

## 决策

将现有归档正式定义为**软删除**：

- 软删除只写入 `TaskCenterArchive`，让记录从默认列表、异常计数和导演跟进中消失。
- 不删除任务、步骤、事件、命令、通知、正文、产物或检查点。
- 不修改任务真实状态。
- 用户可以进入“已清理”视图恢复记录。
- 运行记录可以执行软删除和恢复；这属于记录管理，不属于重试、恢复任务、取消或重规划等工作流动作。

## 用户入口

### 运行记录

页面提供：

- “当前记录 / 已清理”切换；
- “清理记录”按钮；
- 单条终态记录的“清理这条”；
- 已清理记录的“恢复显示”。

“清理记录”打开确认对话框，提供三个范围：

1. **清理历史错误**：所有可清理的 `failed` 和 `cancelled` 记录；
2. **清理已完成记录**：所有可清理的 `succeeded` 记录；
3. **清理所有已结束记录**：所有可清理的 `succeeded`、`failed` 和 `cancelled` 记录。

对话框必须先请求服务端预览，展示将清理多少条、跳过多少条，再允许确认。主按钮使用“清理 N 条记录”。

单次批量最多处理 500 条，按更新时间从旧到新清理；超过上限时提示“仍有更多记录，可再次清理”，避免一个请求无限扩大。

### 导演跟进

页面提供：

- “当前跟进 / 已清理”切换；
- “清理历史跟进”按钮；
- 相同的“历史错误 / 已完成 / 所有已结束”范围。

导演跟进只软删除 `novel_workflow` 类型的导演任务。`auto_approval_record` 是审计记录，不进入软删除选择。导演任务被清理后，应同时从运行记录和导演跟进默认视图隐藏；恢复后同时重新出现。

## 可清理规则

服务端统一判断，前端不得自行决定。

允许软删除：

- `succeeded`；
- `failed`，但不是人工恢复候选；
- `cancelled`，但不是人工恢复候选。

始终拒绝软删除：

- `queued`；
- `running`；
- `waiting_approval`；
- `pendingManualRecovery=true`；
- 当前恢复候选列表中的任务；
- 预览后状态已经发生变化的任务。

本阶段不要求存在后续成功任务，也不要求超过固定天数。因为这是用户主动确认的可恢复软删除，用户可以直接清理仍然碍眼的旧失败。

## 数据行为

- 继续复用 `TaskCenterArchive(taskKind, taskId, archivedAt)`，不新增业务数据表。
- 批量清理使用 `upsert`，重复提交保持幂等。
- 恢复显示只删除对应的 `TaskCenterArchive` 标记。
- 新的拆书运行记录软删除不得再把 `BookAnalysis.status` 改成 `archived`；拆书资产归档和运行记录软删除必须分离。
- 旧版本已经将 `BookAnalysis.status` 写成 `archived` 的记录继续由拆书模块管理，不猜测原状态、不在运行记录里恢复。
- 不实现物理删除、自动过期或后台定时清理。

## API

```text
GET  /tasks?visibility=active|archived
POST /tasks/archive/preview
POST /tasks/archive/batch
POST /tasks/archive/restore
```

预览与执行请求使用相同范围：

```ts
type TaskArchiveScope = "errors" | "completed" | "terminal" | "selected";

interface TaskArchiveRequest {
  scope: TaskArchiveScope;
  entries?: Array<{ kind: TaskKind; id: string }>;
  kind?: TaskKind;
  source: "task_center" | "director_follow_up";
  requestKey: string;
}
```

`director_follow_up` 来源必须由服务端强制限定 `kind="novel_workflow"`，不能由客户端绕过。

范围清理必须扫描对应类型的历史数据，不得只处理当前页面已加载的 80 条。预览列表最多返回 50 条样本，同时返回完整候选数量和是否超过单次 500 条上限。

## 文案

使用：

- “清理记录”
- “已清理”
- “恢复显示”
- “只会从列表中收起这些记录，不会删除任务结果或正文。”

避免：

- “永久删除”
- “彻底清空”
- “错误已解决”
- “修复完成”

## 验收标准

1. 用户可以一次清理运行记录中的历史失败、取消、完成或全部终态记录。
2. 用户可以一次清理导演跟进中的终态导演记录。
3. 排队、运行中、等待确认和等待人工恢复记录无法被清理。
4. 清理导演记录会同时影响运行记录和导演跟进的默认列表与计数。
5. “已清理”视图可以查看并恢复新版本产生的软删除记录。
6. 清理和恢复不会改变任务状态、检查点、正文、产物、命令或通知日志。
7. 重复确认不会产生重复归档数据。
8. SQLite 与 PostgreSQL 行为一致，不需要破坏性迁移。

## 非目标

- 不自动判断旧错误是否已经被新任务解决。
- 不新增“已解决”生命周期或重排导演跟进分区。
- 不实现物理删除或自动清理策略。
- 不把运行记录改造成重试、恢复、取消、审批或重规划入口。
