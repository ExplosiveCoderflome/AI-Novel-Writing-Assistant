# 05 原生审校与补丁请求的只读预检边界

状态：2026-10-23 用户明确批准“该最小只读预检方案，继续开发”。按本文约 60～120 行请求构造隔离范围实施；其他已批准事项继续有效，不重复确认。

实施与验证：只读构造、有效 Prompt 描述、原生配置执行检查、逐次完整请求预算及阶段适配已实现。原生请求逐字段对照 6 项、只读渲染 3 项、执行策略 5 项、预检 7 项、阶段 4 项及物理描述 3 项均纳入最新生产集合 278/278。真实结构化调用/JSON 纠错使用传输替身，无付费模型。完整入口仍须完成正式准备链和来源页恢复，详见 05 报告；本批准不扩大为修改旧规划服务的授权。

## 已核实的入口缺口

`ChapterAcceptanceAssessmentService.invokeAssessment`（338～382 行）在私有方法内部构造实际注册 Prompt 的输入、上下文、写法信号和调用选项。公开 `assess` 会调用模型；公开 `getCacheIdentity` 返回缓存身份，不能提供完整有效消息及输入预算。`ChapterPatchRepairService.repair`（72～113 行）同样把补丁许可、上下文与 Prompt 请求构造封装在执行函数里。

新内核的 `StagePort.describe` 明确只读，不能为了取得请求描述先执行模型，也不能用截断正文或近似 JSON 代替实际输入。审校所在 runtime 目录被冻结，不能直接增加公开预检方法。

## 提议的具体范围

在新内核 `infrastructure/services/prompts/` 隔离约 60～120 行**只读请求构造**，按现有原生调用字段复用注册资产和公开纯上下文/写法函数；不复制审校语义判断、评分归一化、补丁应用、质量策略、缓存、重试、持久化或旧流水线。原生审校仍以 `persist:false` 执行，补丁仍由原服务安全应用。

调用方通过 Prompt 层的只读描述入口解析正式覆盖、模板和结构化输出提示，再计算完整消息的指纹与上下文预算。该描述入口不调用模型、不写数据库；不修改既有执行入口的行为。模型窗口必须来自明确的 provider/model 元数据或配置，未知窗口拒绝执行，不把输出上限或猜测值当作上下文窗口。

新增代码示意：

```ts
buildKernelAcceptancePromptRequest(frozenInput) // 原生同字段、注册资产、完整正文
buildKernelPatchPromptRequest(frozenInput)      // 原生同许可和保护信息
describeEffectivePrompt(request)               // 覆盖、模板、提示和模型配置身份
```

## 验收与限制

- 用实际原生审校/补丁服务捕获其注册 Prompt 请求，与只读构造结果逐字段比较；覆盖原稿、候选事实核对、写法保护和自定义上下文。
- 只读预检不得调用模型或创建业务记录；完整正文超过已知窗口时在请求前拒绝。
- Prompt 覆盖、模板、模型路由或有效选项变化必须改变描述身份；执行前后校验不能发布旧配置结果。
- 实际入口仍须完成来源页恢复、预算追加、进度读取及 05 全部验收，才可认定接线完成。
- 冻结目录保持零修改；不启用开关、不迁移业务库、不合入或发布。

确认依据：03～08 任务级计划的明确规则“适配器不得修改旧服务。旧服务不满足需要时，按停止条件 G1 停下，由我决定是否把实现复制进内核。”本项是只读请求构造的独立责任，不借此前终态持久化批准扩大复制范围。
