# 05 正式准备链：可注入端口与事务边界提案

状态：2026-10-23 用户明确批准“可注入准备端口方案，继续开发”。按本文有限接口例外实施，旧调用保持默认实现，冻结目录零修改；此前只读预检批准继续有效。

## 已核实的接线障碍

- `ChapterExecutionPreparationService.prepare` 先执行 `ensureTimelineReady`，再执行 JIT 合同与 `planner.ensureChapterPlan`。这些步骤可能调用模型和写业务数据，不是只读上下文组装。
- 冻结的 `ChapterTimelineFinalizationService.ensureBeforeGeneration` 会扫描并补写前文章节；它没有接收 V2 当前 worker 租约、授权范围或新内核请求检查点的入口。
- 非冻结的 `ChapterExecutionContractService` 会调用连续性审查和合同生成，再通过卷工作区事务更新卷版本、卷章计划和 Chapter；当前事务只检查部分规划字段，没有新内核的运行归属检查。
- 非冻结的 `PlannerService.generateChapterPlan` 在方法内部读取并构造请求，最后调用 `persistStoryPlan` 的全局客户端事务；它没有只读准备/单独执行/事务提交三个可注入端口。

外围执行前后检查不能使这些业务事务具备相同的租约保护；把 prepare 标成“不调用模型”也不能省略内部模型的输入快照、预算和恢复回执。因此不能把现有公开 `prepare` 直接装到正式入口后宣称完成接线。

## 请求批准的具体调整

将 03 的“适配器不得修改旧服务”对**非冻结规划模块的依赖注入接口**作一次有限例外。保留旧调用方式和默认实现，向新调用方开放可注入端口；冻结的 runtime、production 等目录仍零修改。

1. 在 `services/planner/chapter/` 收拢现有单章规划职责：只读读取和请求准备、注册 Prompt 执行、结果规范化、事务提交。`PlannerService` 保留现有门面；book/arc/replan 不纳入本次调整。
2. 为 `plannerPersistence` 和单章执行合同/卷工作区的相关提交路径注入事务内归属及版本校验；默认旧调用保持原实现。端口只接受通用回调和事务客户端，规划模块不导入 production/director。
3. 为连续性审查、合同生成和章计划请求提供完整实际输入的准备/执行接口。新内核在调用模型之前保存子请求描述、结果及提交回执；恢复只复用已保存结果，不重复付费。
4. 新内核新增准备编排，复用上述规划能力和现有上下文组装。前文时间线只读核对；缺失或人工编辑未收尾时返回来源页处理，不由本章准备隐式补写授权范围外的前文。已授权范围内的前章由内核正常 reconcile 闭合。

预计移动既有非冻结单章准备代码约 350～650 行，新增端口/事务保护与编排约 200～380 行，拆入明确职责目录并遵守 400 行/12 文件约束。数字是评估范围，不授权复制整个规划或时间线调度器；若还需扩展其他职责，先报告实际缺口。

## 验收

- 原规划调用与重构后默认调用使用同夹具，完整 Prompt、规范化结果与持久结果一致；V1、book/arc/replan 不切换。
- 临时 SQLite：准备请求前后退出、模型结果已保存但规划提交未完成、规划提交完成但外层 prepare 回执未完成，恢复均不重复模型或业务提交。
- 新内核内部每个模型请求持久预约并绑定完整输入；未知结果保留领取，明确未发送的拒绝才允许恢复。
- 更换 worker、epoch、策略/模型配置或人工修改章节/卷工作区后，旧执行者不能提交规划结果。
- 授权范围外的前文时间线缺失时只返回处理入口；只读检查不产生模型请求、时间线、规划或控制写入。
- 继续完成真实 productionComposition、来源页恢复/追加预算/取消及全部 05 验收；开关保持默认关闭，不迁移业务库、不提交合入或发布。
