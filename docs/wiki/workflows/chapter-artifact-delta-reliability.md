# 章节资产 Delta 抽取可靠性

## Background

章节正文完成后，系统会从一次统一的结构化调用中提取摘要、硬事实、角色状态、资源和伏笔变化。回填针对审校、修复与版本选择后的唯一保留正文；下一章需要使用该版本的资产事实，不能读取运行中候选稿的变化。

## Current Rule

- 首轮抽取优先保留会影响下一章的核心变化，输入上下文按角色、状态、资源和伏笔窗口裁剪。
- 输入上下文预算由 Prompt Budget Profile 控制，输出上限由抽取调用配置控制。输出上限是完整结构的保护边界，不是要求模型写满的目标；结构化校验关注 JSON 结构和关键枚举，不因普通字段长度略超就重复整章调用。
- V1 保留原有 `adaptive / deferred / strict` 控制策略。V2 由当前生产作业显式选择 `director_v2` 回填策略，不依赖全局开关或调用 V1 自动确认编排。
- V2 必须完成必要增量消费者后才允许下一章。运行中返回 pending；必要回填写入失败保留恢复边界，不发布已完成事实，不消耗正文自动修复预约重新跑章节。
- 已应用必要增量后，额外的伏笔整体校准失败可以返回 degraded 并记录资料债务。该警告不应变成全书重规划；不确定资源提案保留待核对，不伪造已确认状态。
- V2 正常章只做增量；整体伏笔校准保留卷末、AI 结构化风险判断或明确 strict 请求。固定每三章对账仍仅适用于 V1 的既有策略。

## 最终正文恢复契约

V2 在唯一保留正文落库之后、资源回填之前，按 job 和正文 hash 保存最终生产结果。`chapter_pipeline_finalization:v1` 是恢复凭据，不是模型上下文：它保留验收、修复选择和质量债务，不重复存储正文。恢复优先读取凭据，再补回填，因此不会先组装生成上下文或重新调用写作、审校和修文模型。

不同 job 的凭据不能互用，作者修改正文后旧 hash 失效。抽取结果和各消费者的持久检查点继续复用；恢复只补未完成的消费者。缓存完成结果也必须核对当前正文，不能把旧正文的成功结果应用到作者编辑后的章节。

V2 完成投影必须拒绝 `degraded` 且没有 `artifact_delta` 应用事实的历史边界。普通局部质量债务仍按问题策略继续，质量优先显式人工暂停仍由用户恢复。

## Failure Modes

- 输出 token 达到上限且 JSON 不完整：优先缩短资产列表或进入补偿抽取，不重复发送同一大请求。
- Schema 字段轻微超长：保留结构化结果，使用确定性裁剪或归一化；只有关键字段缺失、类型错误或枚举非法才判定失败。
- 同一正文版本反复失败：检查模型输出预算和 schema 复杂度，禁止通过无限重试掩盖问题。
- 服务重启遗留 `running` 检查点：V1 按原资料债务策略继续；V2 等待或恢复同一回填检查点，不能将其归类为正文生成失败或消耗章节修复预算。

## 紧凑输出与事实保护

统一抽取覆盖多个消费维度，不能把同一事件在摘要、资源用途、伏笔说明和角色心智中各复述一遍。Prompt 使用紧凑 JSON 示例，要求无排版缩进、单项说明使用短句、证据优先保留一条足够的正文摘录。没有变化时数组为空，未知可选字段省略；这些是生成指导，不新增会触发整次重试的严格长度校验，也不在收到结果后按数量截断重要变化。

压缩不能损失持有人与所有者的区别、人物伤势和误判、保护秘密、资源不可用条件、时间窗口及风险等级。`readerKnows=false` 等非默认值必须显式输出，不能靠省略字段获得错误的默认状态。角色与关系状态的短摘要、资源短摘要用于后续上下文，即使 Schema 允许省略，也应保留有效变化的衔接信息。

输入分为两组：角色身份、资源目录和伏笔目录组成可复用前缀；角色当前目标、当前状态、资源持有者与所有者、可用性、知识边界、限制、风险和兑现窗口属于逐章读取的动态材料。目录按角色 ID、资源 key、伏笔 key 排序，数据库更新时间和历史证据不进入目录。选中的资产只列一次身份，动态行通过 key 引用，不重复发送完整资产历史。

资源和伏笔保留既有近期条目选择，再对选中集合稳定排序。条目新增、改名、规划修改或预算选择变化都会使对应前缀自然变化；稳定目录不是冻结数据。动态资源行保持完整，不用字符串总长截断切掉尾部限制或 false 知识标记。V2 资源目录或有效对话影响读取失败时，在抽取前报告恢复失败，不能以空资料继续支付模型调用；V1 保留既有容错行为。

厂商显式缓存边界只覆盖静态规则、静态 Schema 骨架和目录；正文、上一状态、账本状态与角色对话影响都位于其后。骨架插入会改变消息下标，边界必须随实际插入偏移，不能误标到动态正文。整体伏笔校准将书级承诺和分卷/章节规划前置，当前卷窗口、最近正文、状态、冲突和审校问题置后，仍要求完整覆盖原有账本来源，不能把整体校准偷偷改成只返回变化项。

Prompt 变更后的首轮命中率、JSON 完整率和实际输出长度需要从后续真实调用验证。测试可证明字段合同和前缀布局，不能证明模型必然遵守紧凑输出或厂商必然命中。
