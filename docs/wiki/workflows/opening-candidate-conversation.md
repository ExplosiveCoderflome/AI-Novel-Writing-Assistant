# 开书候选的讨论、采纳与建书

作者可以在「方向候选」上连续讨论。同一故事有时会在不同轮次生成相似的方案，任务 ID、候选批次 ID 和候选 ID 三者共同确定一次讨论的资源范围。打开助手只读取这个范围的历史。书名用于展示，不能定位讨论或决定采用哪一轮。

作者需要反复对照几套故事。每轮同时展开各套全文，阅读区宽度足够时每行并排两套，空间收窄时每行一套。工作区占满页面可用宽度，阅读区在正文与滚动条之间留出间距。列数取决于扣除助手栏后的实际空间，每套方案的字段排版再按自身栏宽调整。每轮目录按书名定位。通过目录跳读或滚动时，助手继续讨论原先选定的方向，作者可以带着同一个问题对照其他故事。

初次生成和换一批都先定方向再展开。`novel.director.direction_pair@v1` 在共同题材、作者约束和本轮反馈内寻找一处影响整书的选择，为 A、B 各写一句读者能看懂的方向和一种持续推动故事的方式。两个键只用于对应结果。判断分岔是否有意义，要看互换两套的主角行动和阶段回报后，是否仍能讲同一个故事。语义判断交给模型，结构校验检查缺项和完全重复的内容。

`novel.director.candidates@v3` 接收两条已定路线，分别展开冲突、人物、开篇和推进循环。按键把选择句随候选保存，再生成备选书名，书名变化不影响方向归属。单套讨论和定向修正沿用该轮最初的选择句。旧候选没有这项时直接展示原稿。整轮生成成功后才追加到历史。

方向选择句的建议长度服务于并排阅读。只要两条路线完整且有区别，展开方案和保存候选时都保留原句，避免因展示长度丢掉有效方向。整轮候选尚未保存时，从原开书页重试会沿用任务保存的创意与设置，重新生成本轮。

「开书方向构思」和「开书方案展开」各自保存全局规则。方向构思负责从哪里分岔、怎样一句话说清选择、怎样检查路线差异。方案展开负责将既定分岔写进主角选择、开篇与后续推进，再比较两套全文。作者本轮灵感、修改要求和 A/B 路线归属随请求传入。两步独立预览时，第一步提供示例种子，第二步额外带入一对示例路线；正式展开始终使用本轮第一步的实际产出。

首轮命名和「重做标题组」共用 `novel.director.candidate_titles@v1`。两套故事常常共享题设、主角身份和物件。命名时传入本案梗概、冲突、人物选择、推荐平台和同轮另一案的方向（旧方案用梗概）。重做时补入作者意见、当前标题组和同轮其他方案的书名。

挑首选时，先遮住简介、标签和取名理由，按目标读者的眼光只看书名，问“我点开后想看什么？”再对照两套方案，看哪一套能持续兑现这个期待。能靠类型语汇或一个谜面立住的短名、能直接点出人物处境的长名都适用。若只能靠编造的对白或隐喻解释书名，即使和故事共用一个物件，也应重新拟名。由模型做这项编辑判断，点击估分仅供参考。

作者选方向时，先看书名和人物面临的核心冲突，再对照开篇吸引读者的场面，以及此后能持续追读的故事线。「开篇看什么」和「后面追什么」分别读取候选保存的开篇悬念和推进方式。关键词和预计章数供扫读时参考。

书名下优先展示已保存核心冲突的首个完整句子，其余原文接在「完整设定与推荐理由」的「冲突展开」中。旧方案缺少冲突时，书名下显示「一句话故事」。完整设定默认展开，保留方向选择句、卖点、人物成长和推荐理由等资料。排版使用作者当前看到的候选稿，无须重新生成。

同一对方案按字段标识共享网格行，行高由这一对中较长的内容决定。旧方案缺少关键词或其他字段时，对侧有值的行留出对应空位。折叠一套的设定只隐藏本套的字段，下一对方案独立计算行高。新增对照字段时，需要同时指定其行名和所属分组的网格范围。

开书助手位于工作台右侧，栏头显示讨论对象；从这里切换时，阅读区定位到对应方案并标记其书名。初次讨论显示该方案保存的开篇悬念，旧方案缺少这一项时显示故事梗概。两栏分别滚动，窄窗口切换视图。已发送的消息按服务端范围读取，未发送的输入按任务、批次和候选在本页暂存。每套文末的「选用这套」确认对应方案。

「讨论当前方案」和「生成下一轮方向」共用右侧开书助手，作用范围由作者选择的入口确定。「都不合适，换一批」只打开下一轮的要求表单，窄屏同时切到助手视图。单套讨论草稿与下一轮的要求各自保留，作者可以往返比较。点击「生成新一轮」才把历轮方案、选中的偏好和补充要求交给导演追加一批，成功后定位到新一轮的第一套。只有在指定方案的讨论中采纳建议，才会写回该方案的叙事字段。

## 共用对话能力与业务写入

- 客户端 `AgentConversation` 负责消息、追问对象、重送、中断和回复预览。工作台适配器提供请求、结果展示及采纳入口。
- 服务端 `modules/agentConversation` 维护单个范围只能有一轮运行、相同请求幂等、临时流预览和有界历史。模型调用在事务外执行。中断或进程重启后可结束本轮并重新发送。完成轮次和发布业务提案须在同一事务中成功。
- 开书模块 `modules/novel/setup/candidateReview` 从服务端读取候选及该任务的模型配置。注册的结构化提示词结合当前稿、讨论和明确指定的上一份提案决定回复或建议。解释只产生回复，追问产生新建议后，被追问的待审提案才能转为历史。
- 后续工作台可接入相同的对话轮次和组件，但须自行定义资源身份、可编辑字段、版本和写入事务。例如已开书的章节准备要核对章节身份、导演确认阶段和已有正文保护，不能借用候选采纳接口写入。

## 采纳与选用

1. 模型只提交叙事字段的新值与理由。服务端从当前候选补出原文。作者可以勾选其中几项，一次决定后保存实际采纳的字段；其余内容可在后续讨论中重提。
2. 采纳事务同时核对候选版本、原文字段、当前等待选择的任务状态和活动命令。只有选中字段写回任务里对应轮次的候选，版本递增，决定与候选同时落库。重复提交相同决定只读取现稿。更换字段重放、跨候选采纳、版本过期或已进入建书阶段均拒绝。
3. 没有版本号的旧候选按首稿读取。重新生成书名组、原有的整套候选修改也推进版本。带历史批次的导演命令要校验已修订候选，保存开书输入时加并发条件，防止其他窗口提交的旧副本覆盖采纳结果。
4. 选用方向时，建书命令携带作者点选的批次、轮次和候选，服务端从任务记录取得已保存的方向。讨论和采纳均不调度建书、世界准备或正文生产。
5. V2 在候选页提供「选用并逐阶段确认」和「选用并自动准备」。生成候选时还没有决定角色和卷纲该由谁确认，因此首次运行以**选用方向时**的选择为准。同一条建书命令携带所选推进方式及其审批、写作范围，快速开书和恢复候选任务都沿用这个入口。逐阶段确认会先停在角色阵容，选定的角色修改随下一步进入分卷规划。

排查「采纳后书里还是原方案」时，依次核对提案实际采纳的字段、对应批次里的候选版本，以及建书命令的批次和候选。运行记录用于查看，作者在开书来源页讨论和确认。

## 等待候选与恢复

状态写入层在准备候选命令时返回对应任务的并发过滤条件。命令入队与状态更新在同一事务内使用该条件，确保准备后发生的采纳也能拦下过期写入。前端观察候选进度时使用任务的统一恢复状态，进入人工恢复就停止本地轮询。

生成方向、换一批和重做书名均以已接受的命令编号观察进度。排队、持有租约和运行中均可持续超过三分钟。读取进度遇到短暂网络故障时继续观察同一命令。成功时取回该命令保存的批次，失败、取消或租约失效时显示服务端原因。离开页面只结束本地观察；重新打开时从任务详情恢复进度及已保存的候选。待人工恢复的任务由用户在开书页明确重试。
