# 人工章节保存与时间线持久化边界

## 背景

正文保存既涉及编辑冲突，也会使摘要和时间线过期。若在 HTTP 或综合 CRUD 服务里拼接数据库操作，新增入口容易漏掉版本校验或持久同步任务。逐条封装 ORM 方法同样不能表达这些一致性要求。

## 决策

按业务操作划分持久化边界：章节编辑由 `chapterEditor` 拥有，时间线最终提交由 `modules/timeline` 拥有。应用层表达“保存后安排哪些工作”，持久化层表达“哪些记录必须一起成功”。保留现有门面，逐步迁移；不要求所有简单查询都建立仓库接口。

## 当前规则

1. 编辑正文、人物资料修订证明、时间线失效及两类持久同步任务在同一事务。仅正文请求按 `expectedContent` 比较原文，最终写入条件使用原始存储正文；混合字段和旧请求按已读时间版本条件更新。同一毫秒的连续保存也必须产生不同编辑版本。
2. 派生资料只能替换对应当前正文的记录。锁定版本的内部更新不能改变用户的编辑版本。
3. 稳定和降级时间线都必须把事件／钩子／时间锚点与成功 checkpoint 一起提交。失败可留下执行领取或失败记录，不能留下虚假的完成标记。
4. 模型抽取在事务外完成。事务只容纳数据库操作，不因模型调用长时间持锁。
5. 数据库故障与记录不存在不同。checkpoint 唯一冲突可以检查已有执行者；其他存储错误必须保留失败语义。
6. 完成优先的局部质量债仍允许降级完成；本边界不修改质量优先的人工暂停或显式重规划规则。
7. 保存响应只承诺正文与持久责任已提交，不能等待派生资料成功。章节／人物资料和事件／伏笔时间线由各自任务恢复，继续导演分别校验两类结果；摘要或时间线的成功不能代替人物身份确认。

## 故障诊断与验证

保存失败先确认正文、编辑版本及同步责任是否整体回滚；时间线失败先确认事件与成功 checkpoint 是否同批提交，再检查正文是否已被编辑。不得通过清空数据库解决这些问题。

`manualChapterSaveSqlite.test.js` 在独立临时数据库中注入任务登记及成功 checkpoint 写入失败，检查回滚、重试、版本拒绝和并发完成保护。`serverDependencyBoundaries.test.js` 防止应用编排重新直连数据库。
