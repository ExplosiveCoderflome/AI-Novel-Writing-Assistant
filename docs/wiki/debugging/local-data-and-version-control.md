# 本地数据与版本控制边界

## 背景

开发数据库、维护脚本生成的备份和本地配置可能包含小说正文、创作记录或凭据。它们是本地运行数据，进入 Git 后会随源码和旧版本分发，不能作为项目初始化数据。

## 决策

Git 保存数据库 Schema、迁移和经过脱敏的测试样例。本地数据库及其备份由使用者保管；维护脚本生成备份不代表允许将备份提交到仓库。

## 当前规则

- 本地数据库、`server/tmp/` 下的数据库备份和实际 `.env` 配置受根目录忽略规则保护，不使用 `git add -f` 纳入版本控制。
- 提交前检查暂存文件和 `git ls-files`；忽略规则只能阻止新增未跟踪文件，不能移除已跟踪文件。
- 清理误跟踪的数据库前，确认具体文件范围，并将副本保存到仓库外，校验大小、哈希及 SQLite 完整性；不要为清理备份而重置当前开发数据库。
- 仅取消跟踪时使用 `git rm --cached -- <明确文件路径>`。删除本地备份需要用户明确授权，并以已验证的仓库外副本为前提。
- 小说正文、配置值及密钥不进入公开排查记录、Issue 评论或发布说明。

## 示例

检查是否仍有数据库被跟踪：

```powershell
git ls-files -- '*.db' '*.db-*' '*.sqlite' '*.sqlite-*'
git diff --cached --name-status
git check-ignore --no-index -v -- server/tmp/db-backups/example.db
```

`git check-ignore` 命中规则不能代替 `git ls-files` 的检查；已跟踪文件可以同时匹配忽略规则。

## 失败模式

- 最新版本删除文件后，旧提交、标签和其他分支仍可能包含原内容。取消跟踪不是历史清理。
- 清除历史内容需另行明确授权，在隔离副本中验证过滤结果，再处理受影响的远程引用。不要在有未提交改动或其他活动工作树的仓库中直接批量改写历史。
- 历史配置出现疑似有效凭据时，应由账户所有者确认撤销或轮换。删除配置文件、改写 Git 历史都不能使旧凭据失效；不要通过调用服务验证泄露密钥。
