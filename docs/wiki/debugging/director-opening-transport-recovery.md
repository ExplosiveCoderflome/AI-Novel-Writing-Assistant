# 开书候选的传输失败与显式恢复

## 原因分类

`STRUCTURED_OUTPUT:transport_error` 表示模型调用未取得可用响应，例如上游响应流中断。此类错误不能仅凭错误标题认定是 Prompt、JSON 格式或前端问题；应核对保存的命令、供应商、模型、起止时间、原错误及失败节点。密钥和完整请求内容不能出现在排查输出中。

## 当前规则

- 结构化调用沿用统一的有界传输重试与已配置备用模型策略；没有可用响应时不能伪造候选、调用 JSON 修复掩盖网络失败或切换成关键词匹配。
- 原开书页仍负责候选选择。开书失败必须展示为失败和待人工恢复，不得只保留 queued 状态让用户误以为后台仍在执行。
- 原页面继续操作对未关联小说的开书任务调用 `opening-retry`。仅允许重试最新的候选生成、细化、修改、标题优化或确认命令；已有小说和旧正文生产命令必须拒绝。
- 恢复在事务中保留旧失败行、复制原请求为新命令，并清除该开书任务的人工恢复标记。幂等键来自旧失败命令 ID，重复点击复用同一次重试；不能由轮询清除暂停。
- 修好恢复入口只能证明可安全再次调用，不能证明供应商传输故障已消失。不得为了验收自动触发收费调用；由用户明确点击重试。
- 进程退出留下的执行中命令必须核对租约。详情读取可将已过期的开书命令投影为待恢复，但不写任务；显式重试才在事务内标记旧命令 stale 并复制原请求。有效租约不能被重试按钮抢占，没有租约到期证据也不能假定进程已退出。

## 诊断顺序

1. 核对任务尚未关联小说、最新命令类型和失败状态。
2. 读取供应商、模型和时间，避免输出密钥和正文。
3. 区分传输中断、完整响应格式失败、结构校验失败，不能混用修复策略。
4. 核对人工恢复标记、页面回调和实际 HTTP 恢复端点。
5. 用隔离数据库验证原请求保留、失败记录保留、重复点击幂等和旧生产命令拒绝，再由用户实际重试。

## 确认后的路由边界

建书成功后，持久化的 `/lab/director/:novelId` 路由是任务详情、运行记录和开书页导航的共同来源。开书候选历史仍保存在 seed 中，它表示已发生的候选操作，不表示任务仍处于候选选择。读取投影若依据这些历史标记覆盖交接路由，会出现“书和新导演运行已创建，但页面仍返回开书”的故障。排查时必须检查实际任务详情响应，而非只检查数据库字段；回归应覆盖保留候选历史的已交接任务和未确认候选任务两种情况。

## 相关模块

`server/src/llm/structuredInvoke.ts`、`server/src/app/director/opening/`、`client/src/pages/novels/autoDirector/useAutoDirectorCreateController.ts`。这些规则作用于建书前候选，不改变小说章节的质量策略和新导演恢复协议。
