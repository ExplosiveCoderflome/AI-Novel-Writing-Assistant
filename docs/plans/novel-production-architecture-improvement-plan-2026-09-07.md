# 小说生成架构可靠性与扩展能力改进计划

日期：2026-09-07

状态：待实施。本文保存审查结论与实施顺序，不表示功能已经完成，也不授权自动推送、合并或发布。

审查基线：`beta`，`25db3223`。实施前须核对当前分支、相关源码及后续提交，避免修复已解决的问题。

## 1. 目标与边界

面向不懂小说创作的新手，优先保证整本小说连续完成，同时降低后续增加创作能力的开发成本。

本计划解决三个问题：

1. 章节生成、验收、修复与事实提交在失败和恢复时保持一致，减少重复调用和修复倒退。
2. 新能力可以通过明确的生产步骤或上下文提供者接入，减少跨层修改。
3. 用小规模、可复用的验证样本证明改善，控制开发会话额度与产品运行时模型费用。

保留现有统一章节执行入口、Prompt Registry、问题策略快照、即时章节规划、局部修复和质量债机制。暂不整体重写导演系统，不引入通用工作流平台、微服务或新的创作模式。

本轮审查未运行真实整本生成，也未读取用户小说数据库；不能据此断言实际小说质量或线上故障频率。

## 3. 目标执行合同

```text
准备本章规划 → 读取版本化上下文 → 生成并保存工作稿 → 验收
                                                    ↓
                               可选一次修复 → 复审 → 选择保留稿
                                                    ↓
                           时间线终态 + 必需连续性资产提交
                                                    ↓
                         记录质量债 / 策略暂停 / 释放下一章
```

约束：

- 正文可读、质量通过、事实已提交是不同事实，不能只用一个 completed 表达全部状态。
- completion-first 下，普通质量债不阻断全书；quality-first 的显式 `pause_for_manual` 必须停在已保存边界，等待用户恢复。
- 明确重规划、无可用正文、数据完整性和受保护内容冲突继续使用安全停止规则。
- AI 负责创作语义和结构化问题理解；确定性运行时负责校验、预算、幂等、持久化及执行已解析的策略。
- 事实同步失败可以按明确规则降级，但必须返回降级证据，不能伪装为同步成功。
- 保留稿变更后，所有派生产物须能关联到同一正文版本；旧版本结果不得覆盖新版本。

## 4. 分阶段实施

### 阶段 A：固化证据与低成本回归基线

目标：将本次观察转为可重复的行为测试，防止后续按印象重构。

- [ ] 固化 R1–R5 的六项隔离场景，使用真实业务函数和模拟外部依赖。
- [ ] 增加中断位置：修复调用前后、正文保存后、approved 后、资产部分提交后。
- [ ] 核对现有测试，优先扩充同责任测试文件，避免平铺重复测试。
- [ ] 记录现有正常链路模型调用阶段、缓存命中、修复次数、章节推进结果。
- [ ] 为待修缺陷保留明确预期或已知失败记录；提交时不得把已知缺陷测试伪装为通过，也不得无说明破坏默认测试集。

验收：全部场景可在无 API Key、无真实数据库写入条件下运行；报告区分已复现、未复现和未覆盖。

### 阶段 B：验收缓存与自动处理预算

范围：R1、R2、R3、R7。

- [ ] 定义验收输入指纹：正文 hash、实际验收上下文/合同版本、有效 Prompt 版本及自定义覆盖版本、有效模型配置和相关参数。
- [ ] 指纹使用稳定序列化，不包含时间戳等无关波动；无有效依赖版本的旧缓存作为 miss 处理，无需清库。
- [ ] 临时系统失败不进入内存或持久成功缓存；Promise 失败或返回不可复用结果时释放相应缓存项。
- [ ] 核对实例内与跨 Worker 的并发请求合并；若章节领取机制已排他，不再叠加重复锁。
- [ ] 建立章节尝试记录，模型调用前原子领取自动处理预算，记录原因、状态及执行身份。
- [ ] 恢复时复用任务策略快照和尝试记录。区分主动的新修复任务与旧任务恢复，不静默刷新预算。
- [ ] 核对低层网络重试、结构修复重试与业务重试的关系，记录真实调用次数；不要承诺网络超时下恰好调用一次。

验收：同输入复用、相关输入变更失效、临时失败可重试；并发和恢复不超出业务自动处理预算；安全错误不自动重写正文。

### 阶段 C：保留稿选择与连续性提交边界

范围：R4、R5、R6、R8。按 C1、C2、C3 分成独立可验证提交。

#### C1：修复候选与版本选择

- [ ] 保存原稿与修复候选的关联；优先复用现有版本能力，避免新建第二套正文版本系统。
- [ ] 修后复审完成再选择保留稿，保持“最多一次自动修文”。
- [ ] 复用已有两次验收的结构化结果，关注严重问题、义务覆盖、禁止越界和已成立内容；总分仅作辅助。
- [ ] 证据不足或候选新增严重问题时保留原稿，并记录修复未采用的原因。
- [ ] 全部终态资产只针对选定版本提交，候选写作期间不将其当作正史。

验收：修复倒退可保留原稿；局部改善可采用候选；修后验收失败不会丢失原稿；不额外默认添加一次模型评选。

#### C2：区分同步结果与完成状态

- [ ] 把同步返回值改为可判别结果，覆盖 completed、pending、degraded、failed，携带正文版本和已完成产物。
- [ ] 同版本任务正在运行时等待其完成，或显式返回 pending；pending 不写入本地成功缓存。
- [ ] approved/完成投影与“可进入下一章”分别处理，恢复以当前版本的产物检查点为依据。
- [ ] 抽取失败时按事实完整性选择受控重试、最小连续性降级或安全暂停；普通质量债不得被误升级为全局停止。
- [ ] 关闭自动审核的路径仍要满足连续性提交边界，不伪造审核通过证据。

验收：下一章只在必需资产完成或明确降级后启动；每个中断点都能补齐缺失产物；不能因旧 approved 状态跳过必要收尾。

#### C3：抽取与应用可恢复

- [ ] 先保存版本化结构抽取结果，再向摘要、事实、资源、伏笔等消费者应用。
- [ ] 每个消费者声明幂等身份和应用检查点；同数据库内能原子提交的写入使用短事务。
- [ ] 不把模型调用放进数据库长事务；跨消费者使用可恢复的逐项提交。
- [ ] 部分应用失败后复用已保存抽取结果，只补失败消费者；旧正文版本的延迟结果不得覆盖新事实。
- [ ] 在最终写入点检查预期正文版本和现有保护约束，覆盖用户编辑与后台结果交错的场景。

验收：应用阶段故障不重复调用抽取模型；重复恢复不产生重复事实；过期结果被拒绝或保留为历史。

### 阶段 D：让已有步骤体系具备真实执行能力

范围：R9。仅迁移章节生产这一个连贯子系统。

- [ ] 列出实际执行职责与事实投影职责，标清每个步骤的真实所有者。
- [ ] 基于现有 StepModule 扩展执行输入、产物版本、恢复规则和预算信息，不新增平行引擎。
- [ ] 将生成、验收、候选修复、终态提交逐步从隐式循环调用变成清晰的应用能力。
- [ ] 外层导演负责任务目标、范围和调度，章节生产负责本章推进；外层不再另行解释同一质量结果。
- [ ] 状态投影读取步骤结果，避免以“某类产物存在”代替“当前章当前版本已完成”。
- [ ] 手动与自动入口继续复用执行能力，各自保留合法的用户交互差异。

验收：一个仅使用模拟数据的可选步骤能经注册接入、失败恢复并正确投影，无需给主循环添加专用业务分支；已有暂停与恢复行为保持兼容。

### 阶段 E：规划准备与上下文读取分离

范围：R10、R11，并核对规划复用条件。

- [ ] 将 JIT 规划/确保计划等写操作移到显式准备步骤；上下文装配只读取已准备产物。
- [ ] 统一手动与自动合同的结构校验，区分“结构完整”与“与当前创作要求兼容”。
- [ ] 定义上下文提供者合同：适用阶段、输入依赖、优先级、required、token 预算和失败语义。
- [ ] 优先迁移角色硬事实、上一章实际结果、章节义务三个必需提供者，再迁移增强信息。
- [ ] 必需上下文不得被软信息裁掉；缺失时返回明确缺口，不以空数组伪装完整。
- [ ] 在章节边界检查稳定配置和规划版本；验证 API 修改后 Worker 能及时失效缓存。
- [ ] 用户加入新想法时，由 AI 输出受影响范围与建议；运行时校验后只重算受影响的未来产物，保留正文和用户保护内容。

验收：新增一个上下文提供者无需改动章节主循环；纯上下文读取不触发模型生成或规划写入；关键变更能够正确失效相关合同、上下文和验收缓存。

### 阶段 F：事实来源收敛与质量评测

范围：R12 及长期质量证据不足。

- [ ] 将角色真实事件归属纳入统一结构化资产抽取，保留证据和来源章节。
- [ ] 姓名匹配仅作候选定位，不直接写成确定事实；兼容旧时间线，避免批量覆盖历史小说。
- [ ] 建立小型固定样本：修复倒退、局部义务缺口、事实未提交、角色信息差、修改规划、目标终章收束。
- [ ] 正常 CI 使用保存的结构化输出回放；真实模型只用于有限人工发起的抽样评测。
- [ ] 记录每章调用次数、token、耗时、有效修复率、重复故障、质量债和全书完成结果。
- [ ] 检查当前终章完成是否有真实证据，避免只依据章节数量或 UI 标签；先验证再决定是否扩展结局合同。

验收：能够比较同一批样本改造前后的可靠性与成本；“完成小说”与“质量改善”分别报告，不用自评分上升代替完整结局验收。

## 5. 实施顺序与交付门槛

顺序：A → B → C1 → C2 → C3 → D → E → F。

第一批只做 A、B、C。可靠性未验证前，不同时展开步骤重构和上下文重构。

每个阶段完成时提交以下证据：

1. 变更范围与责任边界。
2. 对应行为测试及结果，明确跳过的检查。
3. 暂停、恢复、旧任务兼容和正文保护是否受影响。
4. 适用的模块 README/wiki 更新与残余风险。
5. 可独立审阅的本地提交；beta 集成和 main 发布按仓库流程另行执行。

## 6. 额度与验证成本控制

- 开发会话默认单代理，先定位再精读，避免重复全仓库扫描。每次只处理一个可验收阶段。
- 本文作为续接入口，后续会话先读对应阶段和已完成证据，不重新做完整架构审查。
- Codex 账户额度与产品调用模型的费用分别管理；本计划不预估无法证实的剩余额度或 token 节省比例。
- 回归验证优先使用模拟依赖、源码行为测试和历史输出回放，不依赖收费 API。
- 真实模型抽样前确定样本、模型、最大请求数与输出上限；无明确预算时不运行批量生成评测。
- 默认不跑全套构建、打包和浏览器验收；跨模块合同变化运行最窄充分检查，UI 验收交由用户。
- 复用验证需确认代码、分支范围和运行环境未变化；旧 dist 不作为当前源码验证依据。
- 每阶段只报告关键结果、验证和剩余风险，不反复输出整份计划。

## 7. 数据、分支和文档治理

- 实施运行时改造前建立 `codex/` 功能分支；遵循功能分支 → beta → main，不直接在 main 开发。
- 新增持久化结构优先增量兼容；任何破坏性操作必须有用户批准、具体备份路径及恢复验证。
- 不清库、不重置小说、不通过批量回写修正状态来掩盖运行时问题。
- 本文件属于待实施开发计划，无用户可见功能变化，因此不更新发布说明和 README 最新更新。
- 本阶段尚未确立新的架构事实，暂不将建议写入 wiki；各实施阶段验证后，把稳定规则写入对应 wiki，计划保留范围和验收进度。
- 生产链、导演恢复、Prompt 上下文及事实资产规则分别维护到现有工作流/架构 wiki，避免复制整份计划作为变更历史。

## 8. 后续执行入口

从阶段 A 开始，先核对本计划的基线是否仍适用。完成 A 后进入 B；每阶段以验收证据为完成标准，不以文件拆分数量或测试总数为标准。
